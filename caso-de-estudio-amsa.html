Sistema de gestión de almacén AMSA

Caso de estudio del sistema web de gestión de almacén e implementación de la generación automática de documentos parametrizados según plantillas.

1. Recorrido por el sistema

Esta sección reúne los recursos visuales del caso: un video de recorrido del sistema y las imágenes de sus pantallas principales, tomadas del sistema en funcionamiento.

Las imágenes corresponden a pantallas reales del sistema en funcionamiento.

2. Problema

La gestión del almacén se llevaba a cabo con una aplicación de escritorio en Microsoft Access, que operaba con límites reales en tres frentes:

  • Sin portabilidad ni acceso. La aplicación no podía trasladarse a otras máquinas, porque las llaves de acceso privadas seguían atadas a la computadora original.
  • Procesos manuales. El formulario 1-H, las tarjetas Kardex y las requisiciones de salida se elaboraban a mano en hojas de cálculo de Excel.
  • Pérdida de información e inconsistencias. Se perdía el histórico y los insumos se quedaban obsoletos, lo que producía una diferencia constante entre los registros dentro de Access y el inventario físico real.

El impacto no era únicamente administrativo: alcanzaba de forma directa a la área financiera, específicamente a los departamentos de Almacén y Compras.

3. Restricciones

Debido a la imposibilidad de contratar un servicio de hosting externo, se optó por reutilizar la infraestructura existente del área de Informática alojando el sistema en el servidor local de la institución. Esto permitió realizar el desarrollo y el despliegue utilizando únicamente recursos propios, sin costos adicionales en licencias o proveedores externos. Dichas restricciones condicionaron todas las decisiones de arquitectura posteriores.

4. Decisiones de arquitectura

4.1 Capas del sistema

El sistema utiliza una arquitectura monolítica tradicional Django MVT (Modelo, Vista, Template) dividida en cuatro capas principales:

Vistas y plantillas
Django Templates, Tailwind CSS (CDN), Alpine.js (CDN)
Modelo y lógica de negocio
Python, Django, ReportLab, Redis, Sentry, sentence-transformers
Base de datos
PostgreSQL con extensión pgvector, volúmenes persistentes
Seguridad
Nginx como reverse proxy, CSRF, RBAC, backups con rclone
  • Vistas y plantillas: Generación de HTML en servidor (Django Templates), interfaz estilizada con Tailwind CSS y microinteracciones cliente (autocompletado, modales) gestionadas con Alpine.js.
  • Modelo y lógica de negocio: Núcleo en Python y Django, apoyado por Redis, ReportLab (generación de documentos), Sentry (gestión de errores) y sentence-transformers (vectorización/IA).
  • Base de datos: PostgreSQL con la extensión pgvector para búsqueda vectorial y uso de volúmenes persistentes.
  • Seguridad e infraestructura: Proxy inverso con Nginx, control de acceso basado en roles (RBAC), protección contra CSRF y copias de seguridad remotas con rclone.

Flujo de solicitud:

Navegador → Nginx → Django (Lógica/PostgreSQL) → Renderizado de Template HTML → Navegador

4.2 Contenedores y red interna

El despliegue se realizó sobre una red interna de Docker aislada. Los servicios se resuelven mediante el DNS interno de Docker:

  • web (puerto 8000): Ejecuta la aplicación Django completa.
  • db (puerto 5432): Base de datos PostgreSQL con pgvector.
  • redis (puerto 6379): Servidor en memoria para caché y soporte de la aplicación.

4.3 Publicación y respaldos

  • Publicación: Nginx actúa como reverse proxy en el frontal, recibiendo las peticiones externas y canalizándolas hacia el contenedor web.
  • Respaldos: Copias de seguridad automáticas enviadas a almacenamiento externo en Google Drive mediante rclone.

4.4 Observabilidad

Integración con Sentry para el rastreo de eventos, registro de errores y monitoreo del estado de la aplicación.

5. Capacidades del sistema

5.1 Inventario y catálogo

Módulo de Inventario

  • Visualización de existencias: Muestra el stock vigente de insumos al momento de renderizar la página en el servidor.
  • Sistema de alertas: Notificaciones visuales tipo semáforo para indicar niveles límite de stock.
  • Búsqueda y filtrado: Herramientas para filtrar por categoría y realizar búsquedas específicas por ID o nombre.

Catálogo de Productos

  • Gestión de nuevos ingresos: Control e incorporación de nuevos productos al almacén.
  • Prevención de duplicados: Integración del modelo SentenceTransformers para evaluar la similitud semántica de los textos y evitar registros repetidos.
  • Cumplimiento normativo: Asignación de renglones presupuestarios regida estrictamente por la 7.ª edición del Manual de Clasificaciones Presupuestarias para el Sector Público de Guatemala.

5.2 Entradas

El ingreso de insumos al almacén se gestiona mediante la emisión de la Constancia de Ingreso a Almacén (Formulario 1-H). Para garantizar el control, la incorporación de nuevo stock al inventario debe transitar por un flujo de aprobación con cuatro estados de revisión: Borrador, Pendiente, Aprobada y Completada.

El sistema registra el encabezado del formulario con los campos requeridos y asigna la entrada de existencias a los insumos previamente guardados en el catálogo. Asimismo, genera un archivo PDF cuyo diseño coincide con la versión física del Formulario 1-H autorizado, conservando una bitácora detallada de cambios e historial de edición. Para la seguridad de los datos, el proceso de anulación opera en cascada y valida en todo momento que las existencias no resulten en valores negativos.

5.3 Salidas

El sistema contempla dos métodos para gestionar las salidas de inventario:

Salida Total. Vincula de forma directa la Constancia de Ingreso (Formulario 1-H) y la totalidad de sus insumos registrados, procesando el egreso exacto de la cantidad que ingresó originalmente en dicho documento.

Salida Parcial. Permite el egreso individual por insumo y cantidad solicitada. El sistema valida automáticamente que las salidas no generen stock negativo.

Flujo de Aprobación. Las salidas cumplen con el mismo flujo de revisión y ejecución establecido para los ingresos (Borrador, Pendiente, Aprobada y Completada).

Constancia en PDF. Cada salida genera su constancia en PDF.

5.4 Kardex

Ofrece trazabilidad detallada de los movimientos de almacén mediante filtros por producto y rango de fechas, ajustando automáticamente el saldo inicial. Reporta entradas (con Formulario 1-H, factura, proveedor, precio unitario y cantidad) y salidas (con número de Requisición y cantidad). Incluye la opción de descargar el reporte de movimientos en PDF.

5.5 Búsqueda semántica real

No es simulada. El modelo intfloat/multilingual-e5-small, ejecutado con sentence-transformers, genera vectores de 384 dimensiones en pgvector con índice HNSW y distancia coseno. El embedding se regenera por sí mismo solo cuando cambian el nombre, la descripción o la categoría, mediante un hook sobre Producto.save(). La búsqueda es híbrida: coincidencia exacta de código cuando el patrón corresponde y búsqueda semántica pura en el resto de los casos.

5.6 Bitácora de auditoría

Garantiza la trazabilidad total mediante el registro de acciones operativas, inicios de sesión, descargas de archivos y eventos del sistema. Incluye herramientas de auditoría con filtros por usuario, fecha, acción y módulo.

5.7 Seguridad operacional

Sesión única con protección contra el doble ingreso respaldada en Redis, cierre forzado de sesiones remotas por parte de un administrador, y restablecimiento de contraseña con matriz de permisos y un límite de tres solicitudes cada 24 horas.

6. Alternativas descartadas

  • Plataforma alojada. No se desplegó en un host por falta de presupuesto, que es la razón por la que el sistema corre en el servidor local.
  • Dominio propio. No se registró ningún dominio específico para la plataforma, por lo que se utiliza la dirección IP del servidor dentro de la red interna en la que AMSA opera.
  • Aplicación de escritorio frente a aplicación web. Se decidió construirlo como aplicación web para que más usuarios pudieran alcanzar la plataforma. El acceso está restringido a usuarios autenticados y pertenecientes a la institución.

7. Qué salió mal y qué se rehace

  • Arquitectura. No se eligió una arquitectura de antemano para organizar el proyecto correctamente.
  • Planificación e implementación. La planificación y la implementación fueron rápidas y no estaban bien organizadas.
  • Capacitación. El tiempo de capacitación dado a los usuarios del almacén fue demasiado corto.

8. Resultado

La creación de documentos ocurre ahora en una sola plataforma centralizada, con un margen predeterminado y el esquema correcto, de modo que la documentación queda preservada y registrada.

Toda la información de entrada y salida de insumos está centralizada y registrada en una sola plataforma, y varios usuarios pueden acceder a ella para controlar el flujo con el que se registran las entradas y salidas del almacén.
